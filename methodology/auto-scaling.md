# Объём артефактов — всегда максимальная глубина

Методология doubled-graph **не масштабирует глубину артефактов под размер проекта**. Все проекты — от pet-скрипта до enterprise-репозитория — получают максимальный набор полей и разметки.

---

## Что это значит практически

| Артефакт | Заполнение |
|---|---|
| `.grace/context/requirements.xml` | цели, пользователи, ограничения — свободным текстом (якорей `UC-*` в 4.x нет), каждый пункт однозначно проверяем |
| `.grace/context/technology.xml` | все зависимости, версии, compatibility matrix |
| `.grace/context/principles.xml` | проектные принципы, влияющие на архитектуру |
| `.grace/context/deployment.xml` | окружения, схема выката — или `<Applicability>not-applicable</Applicability>` с причиной |
| `.grace/context/ux-guidelines.xml` | UX-правила — или `not-applicable` с причиной |
| `.grace/graph/main.xml` | все модули `M-*` + `Name`/`Status`/`Summary`/`Path`/`Depends`; data flows `DF-*`; зависимости по транзиту |
| `.grace/verification/main.xml` | `V-<M-id>` для **каждого** `M-*`: `<Priority>`, `<Cwd>`, `<TestFiles>`, `<Command>`, `<Scenario>`, `<Marker>`, `<TraceAssertion>` |
| `.grace/changes/active/C-*/` | бандл (spec + plan) на каждое изменение артефактов; «правок на месте» в `post_migration` нет |
| Разметка кода | `MODULE_CONTRACT` (`PURPOSE`/`SCOPE`/`DEPENDS`/`LINKS: M-*`/`ROLE`/`MAP_MODE`), `MODULE_MAP`, `CONTRACT: fn`, `BLOCK_*` |
| Блоки в функциях | обязательны в функциях > 20 строк |
| Logs | debug + info + warn + error; `belief`, `correlation_id`, `trace_id`, `anchor` в каждом логе |

Исключение — **helper-модули** (пометка в `Summary` записи `M-*` плюс `<Priority>low</Priority>` у его `V-<M-id>`): для них блоки и runtime-контракты опциональны (см. `principles.md § 6 — Пропорциональная гранулярность`). Это не профиль проекта, а свойство отдельного модуля.

---

## Почему максимальная глубина везде

**Четыре причины:**

1. **Робастность ценнее экономии.** Опциональность плодит баги: кто-то не заполнил `Path`, кто-то не написал `V-<M-id>`, кто-то пропустил `Depends` — ИИ тиражирует пропуски. Один unambiguous стандарт — ИИ не угадывает, что заполнять.

2. **Инструменты поддерживают только одну форму.** `doubled-graph detect_changes` и `impact` опираются на `Depends` (вложенные `M-*`/`DF-*`) в `.grace/graph/main.xml` и на покрытие `M-*` → `V-<M-id>` в `.grace/verification/main.xml`. Если в «облегчённом» проекте их нет — drift молча недооценивается. Альтернатива «адаптировать tooling под профиль» — O(N) сложности на каждый профиль, не окупается.

3. **«Pet-проект, не нужен enterprise-стек»** — анти-паттерн. У pet-проекта тоже есть зависимости между функциями. Чем меньше проект, тем **ниже** overhead от полной разметки — файлов меньше, правил столько же. Экономия «2 минуты на pet-проекте за счёт отказа от `Depends`» не окупает последующую потерю orientation, когда pet-проект подрос.

4. **ИИ лучше генерирует по полному шаблону.** Локальные модели среднего размера (Qwen 3, DeepSeek V3, …) при частично заполненных шаблонах склонны импровизировать поля. Строгая схема + structured decoding работают стабильнее на полном наборе.

## Где всё же ориентироваться на размер проекта

Не в артефактах — в **выборе профиля автономии при параллельной кодогенерации** (`safe` / `balanced` / `fast`) и в **количестве approval-gates**. См. [approval-checkpoints.md](approval-checkpoints.md).

- **`safe`** — для проектов с высокими рисками (payments, PII, регулируемая отрасль), новая команда, критические модули. Approval перед каждой волной.
- **`balanced`** (default) — обычный режим. Один up-front approval на весь план, scoped review per module.
- **`fast`** — mature codebase + сильная verification. Один up-front approval, без per-wave gates.

Выбор профиля — на пользователя при запуске, не на основе «размера проекта». Artifact-стек — идентичен во всех случаях.

**Автономность в 4.x** выражается не отдельным артефактом, а двумя вещами:

- `grace module health <M-*>` — готовность модуля к автономной работе: есть ли `V-<M-id>`, не пустая ли она (нет `verification.placeholder`), нет ли открытого дрейфа;
- `.grace/changes/active/C-*/` — активные бандлы изменений: единственный законный способ менять артефакты, и они же ограничивают, что агент вправе сделать без человека.

Профиль (`safe` / `balanced` / `fast`) задаёт частоту approval-gates, а не объём артефактов.

## Что делать, если «я правда хочу меньше артефактов»

Тогда не используй doubled-graph. Частичное применение даёт меньше пользы, чем полный отказ:

- без `V-<M-id>` — нет привязки кода к verification → ИИ может писать код без тестов → нарушение принципа 9 (прослеживаемость);
- без `Depends` — `detect_changes` не видит дрейф → принцип 7 (код — живой документ) нарушен;
- без `<Priority>` у `V-<M-id>` — `impact` и `grace module health` не определяют risk → правки без guard.

Лёгкие методологии, которые **допустимо** смешивать с самим подходом «ИИ + план», есть, например, BMAD-Method, Kiro-flow, spec-kit. Выбирай одну из них, если doubled-graph кажется overkill. **Не пытайся собрать «doubled-graph Lite» своими руками — это и есть анти-паттерн, упомянутый в причине 1.**
